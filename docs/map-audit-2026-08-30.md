# Map subsystem professional audit — 2026-08-30

Scope: the entire **Map tab** and its navigation/location subsystem — the
CrsSimple campus basemap, Google walking-nav, search, favourites, compass /
point-me, wayfinding, and 360°. Method: measure the untouched baseline first,
audit code + docs, run the Maestro E2E suite, then remediate clear defects with
evidence. Baseline commit `33ec637`; remediation merged at `07d0276`.

Evidence tags used below: **Verified** (test / on-device / doc-confirmed),
**Inferred** (code-path analysis), **Unable to verify** (environment limit).

---

## 4. Google walking navigation findings

- **Consent — Verified.** No Google surface initialises before consent resolves
  positively. Tapping Directions raises the disclosure *before* any Google map is
  drawn; declining returns to the campus map with no network (spec §2b). The
  subagent traced re-entry-after-decline and the `mapsSdkReadyProvider` gate — no
  leak. `ConsentGuardedRoutesService` re-checks consent before *and* after the
  await.
- **Routes request — Verified correct.** `POST routes.googleapis.com/directions/
  v2:computeRoutes`; headers `X-Goog-Api-Key` + `X-Goog-FieldMask` (+ iOS
  bundle-id / Android package+cert); a scoped, valid field mask; body with
  `travelMode: WALK` and **no `routingPreference`** (which would be a 400 on
  WALK). Typed error mapping (network / API-failure(status) / no-route / malformed
  / timeout / consent-refused); retry is invalidate-only (billing-safe). QA trace
  carries **no key material**.
- **HTTP 401 — Verified external GCP config, NOT code.** The request is correct
  and keyed; Google's "API keys are not supported by this API" 401 = **Routes API
  not enabled on the project**. See §11. **Unable to verify** a live successful
  route in this environment (no enabled Routes API / restricted keys).
- Minor (P3): `RouteApiFailure` discards the response body, so 401/403/400 can't
  be told apart from logs — a diagnostic gap, not a defect.

Root cause of MAP-006 (for the record): the search/favourites selection moved the
camera **at the cover-fit zoom**, where the artwork exactly fills the viewport so
a non-centre venue can't be centred — the move clamped back to centre and parked
the camera on the constraint edge, which tripped flutter_map's `options=`
assertion (`cameraConstraint.constrain(camera)==camera`) on the dismiss rebuild.
It is an `assert`, so **debug/dev/CI-only** (stripped in release). Fix: select at
`mapFocusZoom` (centerable) — which also improves UX.

## 11. GCP / Routes configuration checklist (to unblock live walking routes)

No code change needed; enable on the SAME project as the key:
1. Enable **Routes API** (APIs & Services → Enable APIs).
2. On the key's **API restrictions**, allow **Routes API** (+ Maps SDK iOS/
   Android for the native map).
3. Use a real **Maps Platform** key (not a Gemini/Agent key); scope region to
   Sydney; register **every** Play App Signing fingerprint (3) for Android.
4. Billing enabled on the project. Then re-run `map-wayfinding` accepting consent
   and confirm a route renders. (Do not request or paste secrets.)
